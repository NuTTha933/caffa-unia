## ทดสอบ Race Condition (`npm run test:race`)

ยิงคำขอ 2 ฝั่งที่ชนกัน **พร้อมกัน** (`Promise.all`) กรณีละ 15 รอบ แล้วตรวจว่าข้อมูลยังถูกต้อง

| # | กรณีทดสอบ | ก่อนแก้ | หลังแก้ |
|---|---|---|---|
| A | ลูกค้ากดแนบสลิปซ้ำพร้อมกัน 2 ครั้ง → ออเดอร์ต้องเหลือสลิปเดียว | ผิด 14/15 รอบ (มีสลิป 2 ไฟล์) | ผ่าน |
| B | ลูกค้าลบสลิปพร้อมกับผู้จัดการกดรับออเดอร์ → ห้ามมีออเดอร์ที่รับแล้วแต่ไม่มีสลิป | ผิด 15/15 รอบ | ผ่าน |
| C | Admin 2 คนลดสิทธิ์กันเองพร้อมกัน → ต้องเหลือ Admin อย่างน้อย 1 คน | ผิด 14/15 รอบ (ไม่เหลือ Admin) | ผ่าน |
| D | ยิงรหัสผ่านผิดพร้อมกัน 30 ครั้ง → ตรวจรหัสได้ไม่เกิน 8 ครั้ง | ตรวจไป 30 ครั้ง | ตรวจ 8 ครั้ง ถูกบล็อก 22 ครั้ง |

วิธีแก้

- **A, B** แนบและลบสลิปใน Transaction ที่ล็อกแถวออเดอร์ด้วย `SELECT ... FOR UPDATE` แล้วตรวจสถานะซ้ำหลังล็อก (ล็อกเดียวกับการรับ/ปฏิเสธออเดอร์ จึงทำทีละรายการ)
- **C** ก่อนนับจำนวน Admin ใช้ `pg_advisory_xact_lock` ให้การตรวจทำทีละ Transaction และนับหลังอีกฝั่ง COMMIT แล้ว (แก้ปัญหา write skew)
- **D** นับครั้งการเข้าสู่ระบบ **ก่อน** ตรวจรหัสผ่าน (เดิมนับหลัง bcrypt ทำงานเสร็จ คำขอที่มาพร้อมกันจึงผ่านการตรวจทั้งหมด)
- สร้างออเดอร์อ่านเมนูด้วย `FOR SHARE` กันการกดปิดขายหรือแก้ราคาในจังหวะเดียวกับที่ลูกค้าสั่ง

จุดที่ป้องกันไว้แล้วตั้งแต่ต้น: เปลี่ยนสถานะออเดอร์ทุกขั้นล็อกแถว `FOR UPDATE` (กดรับซ้ำ/รับพร้อมยกเลิกได้ผลเดียว), ชื่อผู้ใช้และอีเมลเป็น UNIQUE, ลบเมนูที่ถูกสั่งแล้วหรือ Role ที่มีผู้ใช้ไม่ได้เพราะ FK เป็น RESTRICT

## ทดสอบด้วยมือ (หน้าจอ)

- เปิดทุกหน้าด้วยทุก Role แล้วสถานะตอบกลับตรงกับ Access Matrix (200 / 403)
- ตรวจหน้าจอที่ความกว้าง 320, 375, 414, 768 และ 1280 px — ไม่มีการเลื่อนแนวนอน ตาราง ACL / Access Matrix เลื่อนภายในกรอบของตัวเอง

## ปัญหาที่พบระหว่างพัฒนาและวิธีแก้

| ปัญหา | วิธีแก้ |
|---|---|
| ส่งฟอร์มด้วยชื่อ `qty[3]` แล้ว body parser แปลงเป็นอาร์เรย์ ทำให้รหัสเมนูหาย | ใช้ชื่อ `qty[m3]` แล้วตัด `m` ออกที่ Server |
| ข้อความที่ซ่อนไว้สำหรับโปรแกรมอ่านหน้าจอในตาราง Access Matrix ทำให้หน้ามือถือเลื่อนแนวนอนได้ | ให้กรอบตาราง (`.scroll-x`) เป็น `position: relative` |
| ราคาเมนูเปลี่ยนแล้วยอดของออเดอร์เก่าจะเพี้ยน | เก็บชื่อและราคา ณ เวลาสั่งไว้ใน `order_items` |
| Race Condition 4 จุด (สลิปกับการรับออเดอร์, Admin ลดสิทธิ์กันเอง, จำกัดการล็อกอิน) | ล็อกแถว/advisory lock ใน Transaction ดูหัวข้อ "ทดสอบ Race Condition" |

## ข้อจำกัดของระบบ

- ตรวจสลิปด้วยตาของผู้จัดการ ไม่ได้เชื่อมธนาคารหรือ API ตรวจสลิปจริง
- ไม่มีการแจ้งเตือนแบบเรียลไทม์ ลูกค้าและบาริสต้าต้องรีเฟรชหน้าเพื่อดูสถานะล่าสุด
- จำกัดการเข้าสู่ระบบผิดเก็บในหน่วยความจำของ Server (รีเซ็ตเมื่อเริ่ม Server ใหม่)
- บัญชีพร้อมเพย์ในหน้าแนบสลิปเป็นค่าตัวอย่าง ตั้งได้ใน `.env`
